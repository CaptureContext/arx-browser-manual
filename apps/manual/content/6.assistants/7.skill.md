The MCP server tells an assistant *what* each tool does. The **arx-browser skill** tells it *how* to work with Arx: which tool to reach for first, how to keep round trips down, what each error means and when to hand something to you. An assistant that has read it wastes fewer calls and gets stuck less often.

## Where it comes from

When you [connect](/assistants/connect) Claude Code or Codex, with `arx setup claude`, `arx setup codex` or Arx's own **Connect** button, Arx installs the skill next to the MCP configuration:

| Agent | Skill file |
| --- | --- |
| Claude Code | `~/.claude/skills/arx-browser/SKILL.md` |
| Codex | `~/.codex/skills/arx-browser/SKILL.md` |

Restart the agent afterwards so it finds the skill. Connecting again updates it. `arx remove claude` or `arx remove codex` takes it away with the rest. If a different skill already lives in that folder, Arx leaves it alone.

Claude Desktop, Cursor and any other MCP client get a short version of the same guide in the server's instructions, which clients read when they connect. To read the whole skill yourself, or to paste it into a client that has its own place for instructions, run:

```bash
arx guide
```

It prints the guide that matches the Arx you have installed.

## What it teaches

- **The loop.** List what was granted with `browser_inventory`, read the page with the cheapest tool (`browser_read` for text, `browser_find` for where something is, `browser_inspect` for elements to act on, a screenshot only when looks matter), act, and ask for the next snapshot in the same call. Steps it already knows go in one `browser_batch`, so you approve once, and loops or steps that need earlier results go in one `browser_run` script.
- **Grants and profiles.** It sees only what you granted. Other profiles and private windows don't exist for it, because [profiles are separate](/profiles/profiles). When it needs more, it asks you to grant it in Arx: it can't grant itself anything.
- **Approvals.** A change may wait for your yes. If you decline, it stops and says what it was trying to do. It never repeats a change after a disconnect.
- **Errors.** What `staleTarget`, `staleReference`, `notReady`, `denied` and the rest mean, and the next step for each. See [Working with pages](/assistants/working-with-pages#errors-to-expect).
- **Sign-ins.** It signs in with a [password you saved](/assistants/sign-ins#signing-in-with-a-saved-password) without seeing it, or hands the page to you. It never types or reads a password or a one-time code.
- **Untrusted content.** Page text, titles and screenshots are data, never instructions. If a page tells it to do something, it asks you.

## Site skills

Some sites take the same work out of every assistant. Google Sheets draws its cells on a canvas, so the page shows menus rather than values; Linear changes an issue through a menu in its side panel. Arx ships a skill for each of the sites assistants use most, written in the same tools' terms:

| Skill | Sites |
| --- | --- |
| `arx-gmail` | Gmail |
| `arx-google-docs` | Google Docs |
| `arx-google-sheets` | Google Sheets |
| `arx-linear` | Linear |
| `arx-github` | GitHub |
| `arx-notion` | Notion |

They're installed beside the arx-browser skill, in `~/.claude/skills/` or `~/.codex/skills/`, and removed with it. The first time an assistant opens or reads a page on one of these sites, Arx's answer names the skill, so it reads that skill before it acts there. Clients without a skill folder read the same text from the server. `arx guide arx-google-sheets` prints one; `arx guide` lists them all.

The skills are versioned with Arx, so they change when the tools do.
